# RCPP 온톨로지 명세

## 목적과 경계

본 온톨로지는 철근콘크리트 공종의 공사기성부분내역서를 작성하기 위해 필요한
비용 관련 서류의 항목, 수량, 단가, 금액 및 서류 간 정보전달·산정·집계 관계를
의미적으로 표현한다.

사용 서류는 계약내역서, 공사기성부분내역서, 원가계산서, 공종별집계표,
공종별내역서, 수량산출서의 여섯 종류로 한정한다. 검측·품질·안전·공정 서류,
계산 실행상태, 매칭 승인업무, 규격 정규화 엔진과 원본 셀 위치는 비용산정에
직접 필요하지 않아 포함하지 않는다.

## 설계 원칙

- 파일은 나뉘지만 namespace와 ontology IRI가 하나인 단일 온톨로지이다.
- 서류별 품명·규격·단위 속성을 `itemName`, `specification`, `usesUnit`로 통합한다.
- 수량과 금액은 서류명이 아니라 계약·전회·금회·누계·잔여 역할로 구분한다.
- `ProgressDocument`는 산출서류와 근거서류로 구분하며 공사기성부분내역서만 산출서류이다.
- 철근콘크리트공사를 상위 공종으로 하고 철근·콘크리트·거푸집·동바리까지만 분개한다.
- 공종은 클래스와 개체를 혼용하지 않고 `WorkCategory` 통제 분류 개체로 표현한다.
- 비용항목은 네 세부 공종으로 구분하고, 철근과 콘크리트는 비용 성격이 다른 재료비·시공비 하위 유형으로만 직접 인스턴스화한다.
- 단가를 구분하는 상세값은 별도 규격 개체 없이 해당 공종별 `CostItem` 인스턴스의 구조화된 리터럴로 표현한다.
- 수치의 단위는 속성명에 명시하고 값은 `xsd:decimal` 또는 `xsd:integer`로 저장한다.
- 비용정보는 공종 → 규격 → 단위 → 수량 → 단가 → 금액 순서로 식별·산정한다.
- 산식은 계산 실행 개체가 아니라 SHACL 및 검증 코드로 검증한다.
- `SummaryItem`은 개별 수량 단위가 아니라 철근콘크리트 세부 공종별 금액 합계를 나타낸다.
- 문서-항목 소속은 `containsItem`만 저장하며 항목에서 문서는 역방향 질의한다.
- 금회기성수량은 별도 서류가 아니라 공사기성부분내역서 내부 항목의 값이다.
- 기성집계항목은 기관별 서식 차이를 허용하기 위해 선택 항목으로 두되, 존재하면 집계 원천·공종·금액 합계가 반드시 일치해야 한다.
- 철근과 콘크리트 비용항목은 재료비와 시공비 하위 유형 중 정확히 하나에만 속한다.
- 동바리 수량산정 기준은 현재 근거와 단위 코드가 확보된 면적과 공간체적으로 한정하며 `개소`는 제외한다.

## 역량질문과 사용 자원

| CQ | 질문 | 주요 자원 |
|---|---|---|
| CQ01 | 특정 기성항목은 어떤 계약항목에서 계약단가를 받는가? | `providesContractUnitPriceToProgress`, `representsCostItem` |
| CQ02 | 금회기성수량은 어느 항목에서 같은 값으로 전달되었는가? | `providesCurrentQuantityTo`, `currentQuantity` |
| CQ03 | 금회기성금액의 계약단가는 어디에서 같은 값으로 전달되었는가? | `providesContractUnitPriceToProgress`, `contractUnitPrice` |
| CQ04 | 전회·금회·누계·잔여 수량과 금액은 일관되는가? | 수량·금액 공통 속성 및 SHACL 산식 |
| CQ05 | 상세금액은 어느 계약·기성 집계항목으로 합산되는가? | `aggregatedContractInto`, `aggregatedProgressInto` |
| CQ06 | 수량산출서부터 기성내역서까지 흐름을 추적할 수 있는가? | 문서·항목·대응·출처·집계 관계 |

## 용어 근거와 채택 이유

| 개념/속성 | 실제 서류 또는 열 | 필요 이유 | 검증 |
|---|---|---|---|
| `calculatedQuantity` | 수량산출서/산출수량 | 계약수량의 근거 | CQ06 예제 |
| `contractQuantity` | 계약내역서/수량 | 누계 초과 및 잔여 산정 | CQ04, SHACL |
| `contractUnitPrice` | 계약내역서/단가 | 금회금액 산정 | CQ03·04, SHACL |
| `contractAmount` | 계약내역서/금액 | 잔여금액 산정 기준 | CQ04, SHACL |
| `currentQuantity` | 공사기성부분내역서/금회수량 | 금회금액 산정 | CQ02·04, SHACL |
| `previousQuantity` | 전회 기성내역/누계수량 | 누계수량 산정 | CQ04, SHACL |
| `currentAmount` | 공사기성부분내역/금회금액 | 지급액과 공종집계 | CQ04·05, SHACL |
| `itemName`, `specification` | 각 서류/품명·규격 | 항목 식별과 대응 | CQ01·06 예제 |
| 공종별 상세 속성 | 계약내역/규격 | 철근·콘크리트·거푸집·동바리 단가 구분 | SHACL |

정보 전달 관계는 수량산출항목·계약항목·원가계산항목·금회수량항목·전회기성항목의
원천에서 결과 항목으로 향하도록 통일한다. 역방향 출처 관계와 일반 항목대응 관계는
중복 저장하지 않으며, 선택 노드의 수신 관계는 시각화에서 역질의한다.

`SummaryItem`은 계약집계항목과 기성집계항목으로 구분하고 각각 공종별내역항목의
계약금액과 기성금액항목의 금회금액만 집계한다. 원가계산항목은 단위당 재료비·
단위당 노무비·단위당 경비·산출단가를 가지며 세 단위비용의 합과 산출단가를
SHACL로 검증한다. 철근과 콘크리트 비용항목은 재료와 시공 성격을 AND로 강제하지
않도록 각각 재료비항목과 가공·조립/타설비항목으로 분리한다.

`providesCostBasisTo`는 실제 업무기준과 속성 매핑이 확정되기 전까지
`validationStatus "provisional"`인 잠정 관계로 관리하며 핵심 확정 경로와 구분한다.
그 밖의 수량·계약값·금회수량·전회누계 전달 및 계약·기성 집계 관계는
`validationStatus "confirmed"`로 명시한다.

공종별 상세 속성에는 `dcterms:source`를 사용해 2026년 건설공사 표준품셈,
KS F 4009, KCS 14 20 11, KCS 14 20 12의 근거 자원을 연결한다.

실제 열 명칭은 기관별 서식을 대조해 확정해야 한다. 위 표에 근거가 없는 새 개념은
실서류 존재, 기성내역 작성 필요, CQ/SHACL 사용의 세 조건을 충족하기 전 추가하지 않는다.

## 검증 범위

정상 예제는 네 공종 각각에 대해 수량산출→계약·원가근거→공종상세→공종집계
→기성상세·기성집계 흐름을 포함한다. 금회수량은 기성서류 내부 항목으로 기록한다.
철근은 D10·D16 두 상세항목의 계약금액과
금회금액을 실제 합산하며, D16 계약수량은 두 산출항목의 합으로 검증한다. 2회차
기성항목과 3회차 기성항목을 분리하여 전회 누계값과 회차 순서도 검증한다. 2회차
이상은 직전 회차를 정확히 하나 가져야 하며, 각 기성항목의 전회누계 원천도 최대
하나로 제한한다.
철근 재료비와 레디믹스트콘크리트 재료비도 각각 수량산출·계약·원가·공종별내역·
계약집계·2회차 기성·3회차 기성·기성집계까지 완전한 계보를 구성한다.

오류 예제는 필수값과 정확한 카디널리티, 음수, 누계 초과, 계약 및 기성 산식,
산출수량·금회수량·계약값 전달, 계약값의 동일 원천, 전달항목의 단위 일치,
이전 회차 이월, 대응 비용항목, 공종 일치, 계약·기성 집계 불일치를 확인한다.
비용항목의 코드와 이름도 필수 식별값으로 검증한다. 모든 SHACL SPARQL에는 명시적 namespace
접두사를 사용한다.

```bash
python KO/ontology/validate_ontology.py
python KO/ontology/validate_examples.py
python KO/ontology/validate_invalid_examples.py
```

이 검증은 모델 내부 일관성 검증이다. 실제 현장 서류 1건의 열과 값, 현장 전문가
검토가 완료되어야 도메인 정확성 검증이 완료된다.
